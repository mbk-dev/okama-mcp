# okama-mcp 3.1.0

Restores household planning against the published Planner 0.5.1 companion and turns
personal client access into an explicit, per-database local setting. Requires
`okama-planner[reports]>=0.5.1,<0.6.0` and `okama>=4.0.0` (4.0.1 installs by default).

Planner 0.5.1 adds the localized local interfaces — the client form, the meeting journal
and the legacy viewer in English, Russian, German, Spanish and Simplified Chinese. It
keeps the 0.5 API and the database schema, so the paired release changes nothing in the
MCP contract. The development source override is gone: MCP and its CI now resolve the
published companion.

## Personal client data

- Two access modes, `anonymous` by default. `client_data_mode_set` switches to
  `personal_data` and back; `client_data_mode_get` reports the saved mode. The setting
  lives in a sidecar file next to the database (`<database>.mcp-access.json`), is re-read on every
  call, is shared by concurrent connections and survives a server restart. It never
  enters the database schema and contains no client identities.
- Anonymous mode returns pseudonyms and refuses every persistent client write.
  Personal mode enables client create/update/delete, residency notes, plan versions,
  meetings and bounded history through Planner's own API.
- MCP imports no database driver or ORM and executes no SQL. Planner owns every read,
  write, ownership check and transaction rollback.
- Errors stay fixed public captions in all five languages; a refusal on personal access
  has its own caption instead of a generic failure. No input values, local paths, table
  names or schema text reach the assistant.
- Forecasts and reports remain anonymous and are accepted for export only with an
  unchanged, signed privacy proof.
- The legacy `--allow-personal-data` startup flag only initializes an absent policy; it
  cannot override a mode saved through MCP. HTTP still exposes no client or local report
  tools.
- Tool catalog: 52 tools in a standard install; local stdio with client tools and Excel
  export exposes 70.

## Speed

The server gained no new cache in this release. The heavy calls are okama calculations,
and new installations now resolve okama 4.0.1, which reworked its batching and reuse
paths. Measured here on a Ryzen 7 8845H, Python 3.14.8, median of five repetitions,
fresh portfolio object per repetition:

| Path | Workload | okama 4.0.0 | okama 4.0.1 | Ratio |
|---|---|---|---|---|
| `PortfolioDCF.wealth_index()` (`get_dcf_wealth_index`) | 30/70 SPY/AGG, monthly indexed withdrawal, 256 months | 54.7 ms | 6.8 ms | ≈8× |
| `AssetList.get_rolling_cagr()` | 3 assets, 60-month window, 182 points | 37.9 ms | 2.3 ms | ≈16× |
| forecast trio behind `monte_carlo_forecast` | 30 years, 8,192 scenarios | 1.016 s | 0.788 s | not claimed |
| `EfficientFrontier.get_monte_carlo()` (no MCP tool) | 3 assets, 8,192 portfolios, yearly rebalancing | 25.90 s | 0.062 s | ≈418× |

The first two rows have non-overlapping run ranges. The forecast trio overlaps
(0.59–1.10 s versus 0.66–0.88 s), so no improvement is claimed there. Ratios are
workload-specific and must not be multiplied or read as a general speed claim. Pinned
environments need `pip install -U okama` to pick up 4.0.1.

## Local models

The interface defects reported with a local model were fixed in 3.0.0, not here:
complete nested input schemas in `tools/list`, namespace capability descriptions,
actionable RATE/INFL/RATIO corrections, exact-match ranking and pagination for symbol
search. 3.1.0 adds two things that matter for small models:

- a refusal on personal data returns one short localized sentence instead of a generic
  error, so a model does not retry against a misleading message;
- the current access mode is readable by the model (`client_data_mode_get`) instead of
  being guessed from failed calls.

No model-specific improvement is claimed: the replay with the reporter's
`Qwen 3.8 27B Q4_K_M` and client is still open in
[#17](https://github.com/mbk-dev/okama-mcp/issues/17) because the runtime and a
reproducible task are still missing.

## Verification

- `uv run pytest -q` — 402 passed, 35 deselected, Python 3.14.8, okama 4.0.1.
- `uv run ruff check .` — clean.
- Registered tools: 52 without local client integration, 70 with it.
- Release gates install with `--no-sources` and require the published companion before
  upload; the exact PyPI package is then checked without source substitutions.

```bash
uv venv tmp/pypi
uv pip install --python tmp/pypi/bin/python 'okama-mcp==3.1.0'
tmp/pypi/bin/python -I tests/release/published_pair.py \
  --fixtures examples/planner --output tmp/pypi-acceptance
```

Synthetic records only; each run requires a fresh output directory.
[Companion compatibility #6](https://github.com/mbk-dev/okama-mcp/issues/6).

## Upgrade

`uvx --refresh --from okama-mcp==3.1.0 okama-mcp stdio`, or `pip install -U okama-mcp`.
Restart the MCP client so it reloads the tool schemas. Existing local databases keep
their saved access mode; a database without a policy starts anonymous.
